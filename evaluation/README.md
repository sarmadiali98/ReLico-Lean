# ReLico executable evaluation catalog

This directory contains the shared registry and schemas for two semantically distinct suites:

- 61 translator conformance and regression tests under `tests/translator/`;
- 41 source-evidence and application benchmarks under `benchmarks/`.

Both suites use the same artifact-producing pipeline, but they are separated because translator
correctness tests and empirical application benchmarks answer different questions.

## Registry and Current Population

The registry originated as a reviewed 102-row source plan. The current catalog partitions those
rows into 61 translator fixtures and 41 application benchmarks. "Planned" describes the registry's
provenance, not every row's current implementation status; `benchmarks.tsv` and the corresponding
manifests determine current status.

The registry directory contains:

- `benchmarks.tsv` records suite placement, required stages, and implementation status for 102 rows
- obligations.tsv maps all 2,468 Lean test obligations
- shared-formal-evidence.tsv records formal evidence that shares a
  concrete source benchmark
- source-model-plan.tsv records planned source locations
- general-corpus-selection.tsv records the measured construct profile
  of every candidate general-family source model
- legacy-script-migration.tsv records the six obsolete script
  replacements
- coverage-audit.txt records the zero-unmapped-obligation result
- final-b1-summary.txt records the completed B1 review

A registry row is not by itself evidence that its pipeline passed. Committed expected artifacts and
execution records provide test or experimental evidence according to their declared stage and suite.

## Required benchmark contents

An implemented test or benchmark directory must contain:

- `README.md`
- `manifest.json`
- `coverage.json`
- `source/model.rebeca`
- committed expected artifacts for every required stage

The committed `expected/` tree is the executable golden oracle. The runner compares generated bytes
directly with these files; manifest hashes provide an additional integrity check. Software-test run
records are collected under `.test-results/`, while the benchmark pipeline retains detailed
per-stage `actual/` evidence for compatibility with existing manifests. Generated `actual/` content
is execution output, not required committed benchmark content.

## Mandatory execution stages

Every source must first pass through RMC code generation, generated C++
compilation, and model-checker execution.

Applicable later stages include:

- parser JSON generation
- Lean DTR decoding
- deterministic DTR AST output
- formal witness generation
- LF AST translation
- LF source printing
- lfc compilation
- native runtime execution

Negative benchmarks must declare their expected terminal stage. No later
artifact may be fabricated after an expected rejection.

## Runner Interfaces

`tools/relico_test.sh` runs the authoritative translator test catalog. `tools/relico_bench.sh` and
`tools/relico_bench.py` validate, list, inspect, and execute registry-backed fixtures and benchmarks.
See [`tests/README.md`](../tests/README.md) for logical-case counting and evidence semantics.

The current benchmark interface supports:

- registry validation
- benchmark listing
- benchmark inspection
- one-benchmark execution
- all-benchmark execution
- dry runs
- expected-artifact regeneration

Each executed stage retains its command, working directory, stdout,
stderr, exit code, duration, toolchain information, and artifact hashes.

## Legacy cleanup

The six family-specific shell scripts remain compatibility entry points pending completion of the
documented migration criteria. New user documentation should prefer the catalog-backed unified
runners.

## Runner exit-status contract

Registry validation, listing, and inspection return zero when the
requested operation succeeds.

Whole-corpus execution returns:

- 0 only when every planned benchmark is implemented and passes
- 1 when an implemented benchmark fails
- 3 when one or more planned benchmarks are not implemented

An incomplete corpus is never reported as a successful whole-corpus
execution.

## Implementation status contract

The frozen registry is authoritative for implementation status and suite placement.

A benchmark with status `planned` must not contain `manifest.json`. A
benchmark with status `implemented` must contain `manifest.json`. Registry
validation rejects either mismatch.

Corpus execution runs only rows marked `implemented`. Direct benchmark
execution also rejects rows that are not marked `implemented`.

## Evaluation Status

The VMCAI 2027 evaluation suite is still under active development and has not yet been frozen for
artifact submission. Current manifests and registry status describe the repository today; they are
not final paper-result mappings or final artifact reproduction instructions.
