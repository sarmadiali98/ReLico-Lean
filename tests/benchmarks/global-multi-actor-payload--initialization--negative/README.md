# global-multi-actor-payload--initialization--negative

Negative global multi-actor payload initialization benchmark.

The source declares the same two-actor payload fragment as the positive sibling `global-multi-actor-payload--external-send--positive`: a `Sender` reactive class that owns the known rebec `receiver0` and, from its constructor, drives the external send `receiver0.receiveMessage(data)`, together with a `Receiver` class carrying the payload message server. The sole malformation is in `main`: the actors are instantiated in the order `[receiver0, sender0]` instead of the declared topology order `[sender0, receiver0]`. Everything else — the classes, the `knownrebecs` binding, the message-server surface, the priorities, and the finite-liveness `keepAlive` self-loop — is the positive fragment unchanged.

Reordering the `main` instantiations is well-formed Timed Rebeca, and RMC accepts it: the rebecs form a concurrent set and instantiation order carries no runtime meaning in Rebeca. The RMC verdict is therefore `satisfied` (byte-identical to the family verdict of the accepting siblings). The family `global-multi-store-payload` parser engine then rejects the model with the deterministic diagnostic `global_multi_store_payload_initialization_order: actors are initialized in main as ['receiver0', 'sender0'], which does not match the declared topology order ['sender0', 'receiver0']; per-actor initial stores must share the actor domain in declared order (reordered initialization has no valid source-to-target startup alignment)`. The remaining stages record this as canonical expected-absence, expected-boundary, and terminal-diagnostic evidence, and no `parser-json/model.json` or decoded AST is produced.

This rejection is a translation *precondition* (input-domain) boundary, not a source-language error. The verified ReLico startup construction aligns per-actor initial stores *positionally*: `alignStartupEntries` requires the initial-store domain to equal the actor domain in declared order, and `initialStoresWellFormed` uses order-sensitive key-list equality. A `main` whose instantiation order does not match the declared topology order therefore falls outside the fragment for which the translation is proven correct, so the parser refuses the input rather than emitting an unverified translation.

Formal coverage consists of the 52 accepted source-capability obligations in `Relico/Tests/GlobalMultiStorePayloadInitialization.lean`. Among them, `reordered_initial_stores_rejected` (obligation `GlobalMultiStorePayloadInitialization:0020`) establishes that the reordered per-actor initial stores fail the `initialStoresWellFormed` predicate (`= false`), and `reordered_alignment_is_none` (obligation `GlobalMultiStorePayloadInitialization:0026`) establishes that `alignStartupEntries` returns `none` for the reordered domain. Together they show that the parser rejection corresponds to a genuine formal boundary in the verified startup construction rather than a runner-fabricated one.

This benchmark does not claim that the current source frontend decodes global actor topology. It does not claim that reordering `main` changes Rebeca runtime semantics — it does not, and RMC accordingly accepts the source; the rejection is the ReLico translation's positional startup-alignment precondition, an input-domain restriction, not a Rebeca well-formedness error. It does not claim that a reordered initialization is unsafe to execute, only that it lies outside the translation's proven-correct input domain. It does not claim unrestricted environmental send semantics or a global absence of priority requirements.
