# ReLico executable benchmark corpus

This directory will connect the verified Lean development to concrete
Timed Rebeca programs and generated Lingua Franca and C++ artifacts.

## Frozen benchmark plan

The registry directory contains the reviewed coverage plan:

- benchmarks.tsv records the 58 planned source benchmarks
- obligations.tsv maps all 2,129 Lean test obligations
- shared-formal-evidence.tsv records formal evidence that shares a
  concrete source benchmark
- source-model-plan.tsv records planned source locations
- legacy-script-migration.tsv records the six obsolete script
  replacements
- coverage-audit.txt records the zero-unmapped-obligation result
- final-b1-summary.txt records the completed B1 review

A planned registry row is not evidence that a benchmark has been
implemented.

## Required benchmark contents

An implemented benchmark directory must contain:

- README.md
- manifest.json
- coverage.json
- source/model.rebeca
- expected stage artifacts
- actual stage artifacts generated by the runner

## Mandatory execution stages

Every source must first pass through RMC code generation, generated C++
compilation, and model-checker execution.

Applicable later stages include:

- parser JSON generation
- Lean DTR decoding
- deterministic DTR AST output
- formal witness generation
- LF AST translation
- LF source printing
- lfc compilation
- native runtime execution

Negative benchmarks must declare their expected terminal stage. No later
artifact may be fabricated after an expected rejection.

## Planned runner interface

The benchmark runner will support:

- registry validation
- benchmark listing
- benchmark inspection
- one-benchmark execution
- all-benchmark execution
- dry runs
- expected-artifact regeneration

Each executed stage will retain its command, working directory, stdout,
stderr, exit code, duration, toolchain information, and artifact hashes.

## Legacy cleanup

The six historical shell acceptance scripts will be deleted after their
replacement benchmarks are implemented and passing, their documentation
references are replaced, and no tracked caller remains.

## Runner exit-status contract

Registry validation, listing, and inspection return zero when the
requested operation succeeds.

Whole-corpus execution returns:

- 0 only when every planned benchmark is implemented and passes
- 1 when an implemented benchmark fails
- 3 when one or more planned benchmarks are not implemented

An incomplete corpus is never reported as a successful whole-corpus
execution.

## Implementation status contract

The frozen registry is authoritative for benchmark implementation status.

A benchmark with status `planned` must not contain `manifest.json`. A
benchmark with status `implemented` must contain `manifest.json`. Registry
validation rejects either mismatch.

Corpus execution runs only rows marked `implemented`. Direct benchmark
execution also rejects rows that are not marked `implemented`.
