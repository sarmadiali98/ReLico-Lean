# global-multi-actor-payload--payload-binding--negative

Negative global multi-actor payload binding benchmark.

The source declares the same two-actor payload fragment as the positive sibling `global-multi-actor-payload--external-send--positive`: a `Sender` reactive class that owns the known rebec `receiver0` and, from its constructor, drives the external send into `Receiver`, together with a `Receiver` class carrying the payload message server. The sole malformation is the payload argument itself: `sendMessage` forwards the composite expression `receiver0.receiveMessage(data + 1)` instead of the bare parameter reference `receiver0.receiveMessage(data)`. Everything else — the classes, the `knownrebecs` binding, the `main` instantiation order, the message-server surface, the priorities, and the finite-liveness `keepAlive` self-loop — is the positive fragment unchanged.

Adding one to a message argument is well-formed Timed Rebeca, and RMC accepts it: integer arithmetic is legal in a send argument, so the model has the same reachable behaviour as the accepting siblings and the RMC verdict is `satisfied` (byte-identical to the family verdict). The family `global-multi-store-payload` parser engine then rejects the model with the deterministic diagnostic `unsupported_expression:data + 1`. The remaining stages record this as canonical expected-absence, expected-boundary, and terminal-diagnostic evidence, and no `parser-json/model.json` or decoded AST is produced.

This rejection is a *grammar representability* boundary — the payload argument cannot be built as a term of the certified source AST at all. The verified payload expression type `DTR.MultiStorePayloadExpr` (`Relico/DTR/MultiStorePayloadSyntax.lean`) is an inductive type closed under exactly three atomic constructors: `intLiteral`, `stateVar`, and `parameterVar`. It has no arithmetic constructor, and the parser-independent bridge schema `RawMultiStorePayloadExpr` (`Relico/Frontend/MultiStorePayloadSchema.lean`) admits exactly those three kinds, with the decoder `decodeMultiStorePayloadExpr` returning `unsupported expression kind` for anything else. A composite argument therefore has no representation to decode into, so the frontend refuses the input rather than emitting an unverified translation.

What makes this the sharpest boundary in the family is that it required **no change to the engine**: the rejection is raised by the pre-existing expression recognizer `parse_expression`, which accepts an integer literal or a single identifier and nothing else. The boundary is a property of the grammar the translation is proven over, not of a guard added to produce a rejection. Correspondingly, the translation's faithfulness over exactly that grammar is already established in the library by `Correctness.compileMultiStorePayloadExpr_evaluate` and its ordered-list companion `Correctness.compileMultiStorePayloadExprs_evaluateAll` (`Relico/Correctness/MultiStorePayloadStatementCorrespondence.lean`), which prove that compiling a payload expression preserves its evaluation in every state and parameter store. Those theorems quantify over the three atomic constructors and no others, which is precisely why `data + 1` lies outside the certified domain.

Formal coverage consists of the 43 accepted source-capability obligations in `Relico/Tests/GlobalMultiStorePayloadFoundation.lean`, the registry-prescribed obligation set for this benchmark. As for every negative in the suite, the required stages contain no `formal-witness` stage, so these obligations are the benchmark's declared ownership in the registry rather than modules elaborated by this benchmark's own pipeline; they are elaborated by `lake build` as part of the library. They establish the global-model well-formedness, topology-resolution, actor-ordering, and state-correspondence foundation that the payload fragment is embedded in. The payload-grammar evidence specific to this benchmark's boundary is the closed three-constructor inductive type together with the two compilation-preservation theorems cited above; no new obligation was added for this benchmark, and none was needed.

This benchmark does not claim that the current source frontend decodes global actor topology. It does not claim that `data + 1` is invalid Rebeca — it is valid, and RMC accordingly accepts the source; the rejection is the ReLico payload grammar's representability restriction, an input-domain limit, not a Rebeca well-formedness error. It does not claim that arithmetic on payloads is unsafe to execute, only that such a payload lies outside the fragment for which the translation is proven correct. It does not claim that the translation is incapable of being extended to composite expressions, only that the present certified grammar does not include them. It does not claim unrestricted environmental send semantics or a global absence of priority requirements.
